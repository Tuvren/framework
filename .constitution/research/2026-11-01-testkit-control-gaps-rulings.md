# Testkit control gaps: owner rulings

This record preserves the owner's rulings for ADR-0084 and the related task plan. Machine authority remains under `spec/`.

## Owner rulings

- Goal: "we must have a real testkit that can prove an implementation works end to end for a backend, keeping Go, Python, etc for later as a less urgent area to focus on, unless they are key to prove that the testkit works."
- Publishing bar, accepted from the lead's recommendation: zero undetected claims on the three durable profiles (kernel.persistent-reopen, kernel.process-crash, kernel.shared-backend), kernel.memory gaps closed by class, and every certificate lists any undetected claims that remain.
- Ordering: "Everything before what is currently open": the new work goes ahead of every other active epic.
- Lead decision within that goal: Rust reproductions of the memory controls follow the published testkit. Rust keeps running the canonical plans, including kernel.codec, as the second implementation, but it is withheld from the certified fleet until it kills its own tagged controls.
- Controls design: "I trust Fable's judgement. Go ahead with that in mind."
- OD-16 ruled: catalogue codec operations under a `kernel.codec` capability (the recommendation already in the register).
- OD-25 ruled: before-commit holds after all checkpoint writes and before COMMIT, amending ADR-0076 decision 4.
- Memory-backed control run on the host: not required and not linked to a certificate. It runs automatically only when a control fails, as a diagnostic that separates a verifier problem from a backend problem. Memory mutants remain release-CI evidence for the verifier.
- No users exist: breaking changes are fine; delete rather than deprecate or shim.
- Minimal code comments; never hard-wrap prose.

## Code checks and planning choice

`spec/kernel/authority-packet.json` lists six legacy and eleven syscall plans. The Go, Python, and Dart targets invoke `tools/conformance/harness/run.ts` through their adapter manifests (`go/kernel-certification/project.json`, `python/kernel-certification/project.json`, `dart/kernel-certification/project.json`); those manifests select the same packet. `tools/conformance/harness/run-plans.ts` loads every plan referenced by that packet before `tools/conformance/harness/check-selection.ts` filters checks. `tools/scripts/compatibility-report.ts` also derives its inventory from the packet, and `tools/conformance/plan-compiler/validate-plans.ts` separately scans legacy operation sources. Filtering checks alone would leave legacy plans in downstream inputs. An adapter-only plan list would be simpler but would break the packet-to-plan authority flow in `.constitution/architecture/flows/flow-authority-packet-driven-conformance.md`. The temporary legacy packet therefore has a distinct ID: `tools/conformance/plan-compiler/certification-assessment.ts` rejects duplicate IDs and requires catalog IDs to match. The legacy plans adopt that ID and remain report-only, with a separate legacy-owned catalog preserving lossless observation validation. `tools/conformance/certification/provenance.ts` expects catalog, profile, and control references on every packet it digests, so DQ must handle the unprofiled legacy packet without weakening canonical certification. This integration remains assumed until DQ verifies it.

The three adapter initialize handlers echo a supplied nonempty packet ID (`go/kernel-conformance-adapter/main.go`, `python/kernel-conformance-adapter/src/tuvren_kernel_adapter/__main__.py`, `dart/kernel-conformance-adapter/lib/adapter.dart`). The ID change therefore appears possible without migrating their kernels, but this remains an inference until DQ runs their conformance lanes.

The control gate reads one configured packet and its manifest, profile, and loaded plans (`tools/conformance/meta-conformance/negative-controls.ts`, `tools/conformance/meta-conformance/negative-control-config.ts`). DK needs the canonical packet, verifier inputs, and existing lane baselines; DL needs the TypeScript binding and the backend-suite obligation audit (`.constitution/tasks/epics/EPIC-DK-portable-certification-core.yaml`, `.constitution/tasks/epics/EPIC-DL-published-backend-testkit.yaml`). Neither task text requires the other three kernels to migrate. It is inferred that both can proceed after quarantine, subject to the DQ checks and unchanged legacy-lane observations.

The two legacy protocol files contain 54 deterministic-hash assertions and 14 canonical-rejection assertions (`spec/conformance/kernel/plans/kernel-protocol-core.json`, `spec/conformance/kernel/plans/kernel-protocol-extended.json`). The pre-change memory register has 40 entries; the expanded codec and core inventory must be recomputed. That baseline includes the schema-roundtrip aggregate and 17 fixture entries (`spec/conformance/kernel/kernel-memory-undetected.json`).

Fable's statement that durable lanes already run all mutants on SQLite and PostgreSQL is too broad: the 15-control manifest has 14 implementation controls and one instrumentation control, and each durable profile currently tags only one control (`spec/conformance/kernel/negative-controls.json`, `tools/conformance/meta-conformance/negative-control-config.ts`). Fable's runner-process activation-counter claim is also not current behavior: the TypeScript adapter selects the counter in its own process and exposes it through the activation operation (`typescript/kernel/conformance-adapter/src/host.ts`, `typescript/kernel/testkit/src/lib/kernel-mutant-registry.ts`). An in-process backend is not isolated from malicious code; no unforgeability claim is made.

The link already compares the implementation string, adapter name, and adapter-manifest digest (`tools/conformance/certification/control-link.ts`). The required change is to bind the actual implementation and its profile-specific control outcomes to that comparison. The proposed one-call-per-transaction mutant is unrun. `RuntimeBackendTx.now` is optional (`typescript/kernel/protocol/src/lib/kernel-types.ts`), so the proposed clock capture applies only when the backend supplies it. SQLite checks the stored tree and path invariants at each write-set commit (`typescript/kernel/backends/sqlite/src/lib/sqlite-transaction-validation.ts`, `typescript/kernel/backends/shared/src/lib/backend-invariant-state-validation.ts`), so it is inferred that a tree committed before its paths will fail. The spike must measure this and other backend invariants rather than assume foreign-key order alone suffices.

## Review-round lead decisions within the owner's goal

The lead decisions below implement the owner's end-to-end backend proof goal. They are not additional owner quotations. ADR-0084 records the architectural decisions and rejected alternatives.

- The legacy packet owns a separate catalog of the 21 composite operations. It declares the exact transitionalAdapters manifest-path set, enforced by the portability gate together with the revised AL topology inventory and companion. Sharing a foreign catalog fails packet ownership; omitting the catalog loses observation validation; exempting transitional packets from coverage can hide plans. DQ deletes TypeScript and Rust composite handlers and fixes the hard-coded generator packetId. Later ports retain handlers until they drop the packet and declared adapter entry together. Their unprofiled tuvren.kernel.protocol certified entries are withheld with a stated reason until canonical certification.
- Aggregate verifierAuthority includes legacy paths only for selecting adapters. Both module and filesystem equality checks use that same selection and include undetected registers.
- DP005 removes Rust from certified and from matrix certificate rows, retaining its positive conformance lane, negative-control diagnostic, and matrix implementations suite result. The existing 13 controls, 3 kills, and 10 unsupported baseline stands until DS. Control kills and report validity become per implementation, with tests against borrowed TypeScript kills and against a Rust diagnostic invalidating TypeScript. DQ requires TypeScript kills and a Rust positive run; DS retains codec and scope reproductions and covers all subsequent memory controls. New mutants record Rust unsupported reasons; a positive assertion Rust cannot pass stops and routes to DS without blocking testkit publication.
- DP depends on DO because both rewrite reports/compatibility. DO also owns the plans, meta-conformance and harness changes its race and reopen controls require. The register schema is pinned here as a claimId-to-nonempty-reason object and linked to DP003; DO precedes its schema implementation. The conformance-plan named-instance shape is pinned by this ruling, while its implementation remains unverified until DQ002.
- Fleet-wide conditional-branch coverage remains release-CI evidence about the plans under ADR-0079 decision 4. A host certificate requires only the branch selected by the backend's observed capability. DP005 owns the link mechanics and DN002 proves certify behavior.
- Every backend claims kernel.memory; durable backends add their durable profiles. SQLite and PostgreSQL run their own core controls, with a SQLite testkit barrier and kernel.barrier capability. Core findings use normal triage. RuntimeBackend-only checks belong to the TypeScript kernel.backend-spi profile; syscall-observable round trips and mutants stay in existing memory and durable profiles.
- First-party server-clock checks use the harness's read from its provisioned database. A foreign substrate supplies a host-side server-clock reader; without one neither clock.backend-server nor kernel.shared-backend can be claimed.
- The testkit-undetected-claims publish-preflight gate in tools/scripts/publish-registry.ts rejects nonempty durable registers and memory reasons without a referenced closed OD. Remaining memory reasons include that OD id and the gate verifies closure. DR005 ends empty or stops for an owner ruling, never a proposal. DO002 depends on OD-21's rollback interim and its acceptance is re-checked after the owner rules. Durable registers cannot close while OD-21 is open; this pass does not rule on it.
- DN003 follows DN004 and proves process-crash and shared-backend kills through public entries. The packed foreign fixture backend uses no first-party backend imports, persists across real reopen, and certifies kernel.memory, kernel.persistent-reopen, and kernel.process-crash with real child death and fresh-process recovery. Only published-testkit certificates require the in-process statement.
- DG, DH, and DI run serially because they change shared negative-control configuration, provenance, certified inventory and the transitional adapter list. Each stops before starting to replan its unmeasured five-point controls against DS's fifteen-point actuals, and deduplicates scope-isolation plan selection.
- Size requires DT: adding codec detectors and durable core proof to DR's existing 15,000-line forecast would exceed the review guidance. DT owns the durable-core prerequisite at 5 points and 10,000 estimated authored lines; DR owns codec detectors in KRT-DR006 and retains 25 points and 15,000 lines and follows DT. No other epic is added or split. DN006 rises from 2 to 5 points for the foreign durable packed proof. Calibration remains approximately 711 historical diff lines per point, including generated evidence; authored forecasts are assumed and need measurement.
