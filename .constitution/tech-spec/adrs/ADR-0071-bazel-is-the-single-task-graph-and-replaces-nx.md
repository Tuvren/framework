### ADR-0071 Bazel Is the Single Task Graph and Replaces Nx

- **Status:** accepted. Supersedes ADR-0013. The `devenv` half of ADR-0013 is retained by this record.
- **Context:** Nx orchestrates 57 `project.json` projects that are all `nx:run-commands` wrappers around native tools, while the real lane logic lives in `tools/scripts/verify.ts`, `check.ts` and `verify-kernel.ts` with hard-coded project lists, `nx affected` and `--skipNxCache`. Bazel is a small island: one hermetic Rust crate and 17 `native_binary` shims that call `bun run nx run`. The owner wants Bazel as the single graph, cache and affected layer with no Nx.
- **Decision:**
  1. **Bazel is the single task graph.** Bazel (bzlmod, pinned through `.bazelversion` and bazelisk) owns targets, caching and affected detection for every language. Nx is removed. The execution models are ADR-0072 (TypeScript, Bun-executed actions) and ADR-0073 (every other language, Bazel-native rules with a recorded exception).
  2. **`devenv` stays the environment entry point.** It provisions Bazelisk, Bun, and the services. Environment pinning lives in Nix and devenv configuration, as ADR-0013 said.
  3. **Retire the lane commands.** `check`, `verify:kernel`, `verify:kernel:fresh` and `verify` are replaced by named `bazel test` suites. Nx-based commands and project-name commands are rewritten in `CLAUDE.md`, `guidelines.md`, the NFC meters and the constitution's verification commands in the same change that removes them. The suite names are chosen by the implementing epic.
  4. **No remote cache.** Local disk cache for developers. CI persists Bazel's disk and repository caches through `actions/cache` (or `bazel-contrib/setup-bazel`) and disables cache saving on pull requests. A hermetic distinction that a shared cache would need is not a goal.
  5. **Service-dependent checks are tagged tests.** The Postgres tests, the gRPC interop smoke, the SQLite and Postgres scenarios and the Gemini scenario are Bazel tests tagged `manual` and `external`, run through named suites, with credentials and connection strings passed through `--test_env`. Bazel never manages service lifecycles. `services:up` stays a manual session step and is never embedded in a target. This replaces the recorded "Postgres exception" in the `MODULE.bazel` and `ci.yml` headers.
  6. **Affected detection.** The implementing epic selects `bazel-diff` or `target-determinator` on measured cost. Until one is adopted, CI runs the full suite.
  7. **Project identity.** Today's Nx project names become Bazel target names, so evidence files and certification manifests that embed them stay valid. Tags such as `boundary:*` and `layer:*` are declared in a Starlark macro. The discovery gates read a generated manifest or parse `BUILD.bazel` files statically. A sandboxed test never calls `bazel query`.
  8. **Gates that read git run outside the sandbox.** `worktree-guard`, `changeset-check`, `check`, `publish-registry` and `kernel-interop-governance` become `bazel run` targets or plain CI steps. The worktree-purity guard becomes a `git diff --exit-code` step after the test suite.
  9. **Generated-artifact freshness is a Bazel action and a diff.** Generators become actions that produce outputs, with a test that diffs them against the checked-in files and a `bazel run` target that writes them back (ADR-0027). The `regenerateCommand` fields in the authority packets and the allowlist in `tools/scripts/lib/regenerate-command-argv.ts` change in the same change. A generated file that is gitignored is a Bazel output, not a bootstrap step.
  10. **Nix accommodations.** PATH is pinned through a `user.bazelrc` generated by devenv, with `--incompatible_strict_action_env`, so action keys do not thrash across shells. `linux-sandbox` is unavailable on NixOS because its startup probe runs `/bin/true`, so NixOS developer machines run the processwrapper sandbox while CI on ubuntu runs `linux-sandbox`. The NixOS-only actions that use Bazel's fixed `/bin:/usr/bin` PATH need an accommodation (NixOS `services.envfs` is a candidate that was not tested).
  11. **CI job names describe reality.** The two check names pinned in ADR-0069 are renamed to match one Bazel gate, and ADR-0069 is updated in the same change. The repository owner updates the branch protection setting. `release.yml` keeps its filename because npm trusted publishing matches on it.
  12. **Release builds through Bazel.** `publish-registry.ts` builds with Bazel and publishes from a staging directory populated from `bazel-bin`, rehearsed with a dry run before Nx is removed.
  13. **Cut over side by side.** Nx and Bazel run together while the graph is ported. Nx, `nx.json`, the 57 `project.json` files and `tools/run-nx.mjs` are removed in the final milestone, after parity is measured on the same commit.
  14. **Dependabot.** Add the `bazel` ecosystem (supported for Bazel 7, 8 and 9) and remove the `nx-toolchain` group.
- **Alternatives considered:**
  - Keep Nx and grow the Bazel island. Rejected by the owner.
  - Hermetic `rules_js` for TypeScript. Rejected by SPK-KRT-OD005 and by the recorded finding that it has no `bun.lock` support (aspect-build/rules_js issue 1258 is open and unfunded); see ADR-0072.
  - A remote cache. Deferred by the owner. The decision does not preclude adding one.
  - No second design was requested. The owner ruled the choices in the session and spikes measured the open ones.
- **Consequences:** Assumed until observed. The Bazel port is large and splits across epics. Two systems run during the cut-over. Every constitution record that quotes an Nx command or a project name is rewritten. Bazel needs a hermetic C toolchain (ADR-0073), and the NFC meters NFC-01 to NFC-09 must keep a runnable command through the change. SPK-KRT-OD005 could not verify the TypeScript model under `linux-sandbox`, so sandbox behavior on the ubuntu CI runner is untested for it. Affected-test selection is unproven until a tool is adopted.
