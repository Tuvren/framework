### ADR-0084 Implementation-matched negative controls

- **Status:** accepted. Amends ADR-0079 decisions 1, 3, and 4; ADR-0081 decision 3; and ADR-0082 decisions 7, 8, 10, 12, and 15; and ADR-0076 decision 1. OD-25 separately amends ADR-0076 decision 4. The owner ruled the control design and publishing bar in `.constitution/research/2026-11-01-testkit-control-gaps-rulings.md`.
- **Context:** A memory-only run proves sensitivity of the verifier and reference kernel in that runtime. It cannot exercise durable profiles: `spec/conformance/kernel/profiles.json` requires `kernel.persistence.durable` for each of the three durable profiles. A memory-only control run therefore supplies no durable-profile controls and cannot support a durable certificate. The manifest contains 15 controls, including 14 implementation controls and one instrumentation control (`spec/conformance/kernel/negative-controls.json`). Only controls tagged for a profile are selected by its gate (`tools/conformance/meta-conformance/negative-controls.ts`).
- **Decision:**
  1. **Control the implementation under test.** An implementation control is a test-only defective seam wrapper over the actual backend, kernel, codec, or fault-injection seam. Run it over the positive run's implementation, substrate, transport, and process boundary. Observation and instrumentation controls retain their distinct expected-rejection rules. A kernel-only mutant such as `kernel.drop-uncommitted-staged-result-on-recovery` tests verifier sensitivity to its altered kernel observation, not the substrate's behavior (`typescript/kernel/testkit/src/lib/kernel-mutants-protocol.ts`). Activation must be proven separately from fault activation; a broken wrapper, missing activation, setup failure, or timeout is invalid, not a kill.
  2. **Match the linked run.** A complete certificate links the passing control run for the same profile and configuration. Match implementation identity, adapter-manifest digest, and all verifier-authority digests. `tools/conformance/certification/control-link.ts` already compares the positive run's adapter, adapter-manifest digest, and implementation string against an entry in the control run; the change is to ensure the entry and all required kills describe the actual host backend and configuration, including a host-declared identity, rather than adding an implementation comparison that already exists. For the published testkit, the certificate states that the control run ran in-process within the binding and backend runtime. That statement does not assert that a separate CLI harness or process-crash supervisor shares the backend's process. Transport and process-boundary fields describe the positive run separately. The process-crash lane must retain its real process boundary.
  3. **Require profile controls.** For each claimed profile, every manifest control tagged for that profile must be killed in the same runtime and configuration as the positive run. A claimed control that survives, is invalid, or does not activate withholds the certificate. An out-of-tree host cannot declare a control unsupported or supply an unsupported reason to make its profile pass. Unsupported fault-point applicability remains governed by ADR-0082 decision 7; it is not an exemption from a tagged control. An unmutated baseline must pass the designated checks before mutation, and those same designated checks must pass again unmutated after the mutant run. A kill requires activation and its designated semantic failure, or the specified rejection for an observation or instrumentation control. Collateral failures alone do not count.
  4. **Separate verifier diagnostics.** Release CI runs the reference memory mutants as verifier evidence. A host memory-backed control run is neither required nor linked to the certificate. When an implementation control fails, automatically run the reference memory controls as a failure-only diagnostic and report both results; that diagnostic cannot turn the failing implementation control into a pass. The trust model remains first-party verification (ADR-0075 decision 1). In-process code is not a security boundary against a dishonest backend; missing activation is invalid, and the published-testkit certificate discloses the in-process execution boundary.
  5. **Fault seam and portability.** The generic non-atomic backend mutant sits under the testkit fault seam, so a hold observes writes the mutant has already made durable. Its feasibility and detecting assertions remain assumed until the spike runs on SQLite and PostgreSQL. Controls must wrap frozen backends without mutating them and load without `node:async_hooks` on the public core import path. The current durable mutant changes `close` with `Reflect.set`, and the stale-head and worker-clock mutants import `node:async_hooks` (`typescript/kernel/testkit/src/lib/kernel-mutants-durable.ts`, `typescript/kernel/testkit/src/lib/kernel-mutants-storage.ts`, `typescript/kernel/testkit/src/lib/kernel-mutants-clock.ts`).
  6. **Expose undetected claims.** Every certificate lists the claim IDs and nonempty reasons from its profile's undetected register, including an empty list when none remain. Use one schema at `tools/schemas/certification-undetected-register.schema.json`: each register is an object whose keys are unique claim IDs and whose values are nonempty reason strings; no unclaimed or detected claim may remain in it. The kernel packet's `undetectedRegisters` object maps each declared profile ID to a repository-relative register path. The control gate validates the schema, checks the profile and claim inventory in both directions, and includes the selected register in verifier-authority provenance. The existing registers are plain claim-to-reason objects and are read through configuration rather than packet references (`spec/conformance/kernel/kernel-memory-undetected.json`, `tools/conformance/meta-conformance/negative-control-config.ts`).
  7. **Publishing bar and order.** Before publishing the testkit, the `kernel.persistent-reopen`, `kernel.process-crash`, and `kernel.shared-backend` undetected registers must be empty. Close the `kernel.memory` gaps by rule class; any remaining claim must name its closed OD id in the reason string and have a closed owner ruling, and every certificate lists what remains. The named testkit-undetected-claims gate in tools/scripts/publish-registry.ts preflight rejects any nonempty durable register and any remaining memory entry without a referenced closed OD in .constitution/reports/open-decisions.yaml. A proposed or unknown ruling cannot satisfy it. New control and legacy-isolation work precedes DK, DL, and DN; DK and DL do not wait for the Go, Python, and Dart migrations or DJ. Rust reproductions of the memory controls follow DN, DG, DH, and DI follow them, and Rust stays outside the certified fleet until its implementation kills its own tagged controls. DJ deletes the remaining legacy plans after those ports migrate. This amends ADR-0082 decision 15. Apply the same memory rule to spec/conformance/kernel/kernel-backend-spi-undetected.json: it is empty, or each remaining entry's reason names a closed OD; reject missing, unknown, or open OD ids.
  8. **Keep legacy validation intact.** The six legacy plans move to `tuvren.kernel.legacy`, which owns `spec/conformance/kernel/legacy-operations.json` containing the 21 composite operations removed from the canonical catalog. Keep lossless observations and observation-schema validation for selecting lanes. The temporary packet has no certification profile or control manifest. It declares `transitionalAdapters`, an exact set of adapter-manifest paths; the portability gate requires exactly those adapters to reference it. Ordinary packets retain boundary-wide coverage. DQ updates the AL topology inventory and companion, packet and manifest schemas, guardrails, and generator packet selection, and deletes TypeScript and Rust composite handlers. Go, Python, and Dart keep handlers until each drops the packet and its declared adapter entry in one ticket; DJ deletes the unused legacy catalog and packet. Their unprofiled `tuvren.kernel.protocol` certified entries are removed with a stated reason until their canonical `kernel.memory` certification. They retain positive inventory and matrix implementation results.
  9. **Digest only selected authority.** Aggregate `verifierAuthority` excludes legacy packet, catalog, plan, and legacy-only fixture paths for adapters that do not select that packet, and includes those paths for adapters that do. Global validation does not make an unselected file a run input. Module and filesystem sources must agree for the same adapter selection, including packet-referenced undetected registers; the generator and freshness check include those registers.
  10. **Match outcomes per implementation.** `control-link.ts` must not union kills across fleet reports or let another implementation's invalid report invalidate the tested implementation's link. Rust leaves `certified`, keeps its positive canonical lane and negative-control diagnostic, loses its matrix certificate row, and retains the suite result in matrix `implementations` until DS. The original diagnostic subset remains 13 controls, 3 kills, and 10 unsupported; new controls extend the diagnostic inventory without changing those original counts before DS. New memory mutants get explicit Rust unsupported reasons until DS; a new positive assertion Rust cannot pass stops and routes to DS rather than blocking testkit publication. DS covers all new memory controls, including codec and scopes.
  11. **Select the observed branch.** ADR-0079 decision 4's fleet-wide conditional-branch coverage remains release-CI evidence about the plans. A host certificate requires the branch selected by the backend's observed capability to be evaluated; it does not require the other branch. DP005 owns the control-link change and DN002 proves the public behavior.
  12. **Certify core rules on every backend.** Every backend claims `kernel.memory`, whose atomicity, native-error, concurrency, and retained-process recovery rules also apply to durable storage. Durable backends add their durable profiles. This clarifies ADR-0076 decision 1 without renaming the profile. SQLite must supply the testkit barrier and capability required by the complete core profile. Each backend runs its own controls; findings use normal triage and cannot be hidden by durable-only claims.
  13. **Separate the TypeScript SPI profile.** `RuntimeBackend` is a TypeScript interface. Put checks observable only through it in a distinct `kernel.backend-spi` profile claimed by TypeScript backends, amending ADR-0082 decision 7's same-profile statement. Syscall-observable round trips remain in `kernel.memory` and the applicable durable profiles, with mutants tagged accordingly; Rust reproduces those memory controls, not TypeScript SPI controls.
  14. **Read the substrate server clock.** First-party checks compare observations with a clock the harness reads from the database it provisioned. An out-of-tree substrate supplies a host-side server-clock reader. Without one, neither `clock.backend-server` nor `kernel.shared-backend` is claimable.
  15. **Prove durable publication through public entries.** DN003 follows DN004 and proves process-crash and shared-backend control kills through public entries. The packed consumer uses a foreign fixture backend without first-party backend imports, persists across a real reopen, and claims `kernel.memory`, `kernel.backend-spi`, `kernel.persistent-reopen`, and `kernel.process-crash`. It proves forced child death and fresh-process recovery with matching activation receipts, same-implementation controls, and complete certificates outside workspace links.
- **Alternatives considered:**
  - **A: memory controls only.** Rejected: they exercise no durable profile and cannot link a durable certificate.
  - **B: implementation-matched controls, with memory controls in release CI and as a failure-only diagnostic.** Chosen by the owner: the control exercises the certified substrate while the memory diagnostic preserves a way to investigate verifier defects.
  - **C: require both memory and implementation control runs on every host.** Rejected by the owner: an additional host memory run is not required to certify the backend and is useful as a diagnostic when a control fails.
  - **D: share the canonical catalog with legacy plans.** Rejected: packet ownership validation rejects a catalog owned by another packet. Leaving composites in canonical authority would also leak legacy operations into published inputs.
  - **E: give legacy plans no catalog.** Rejected: run-plans.ts and run.ts would lose lossless observations and observation-schema validation for the retained lanes.
  - **F: use adapter-only plan filtering or exempt transitional packets from coverage.** Rejected: filtering breaks packet-driven discovery, and an exemption permits plans to disappear from a lane silently. An explicit exact adapter set preserves the gate.
- **Consequences:** Assumed until exercised. Backend-specific nondeterminism can still cause a mutant failure; the unmutated rerun bounds that risk but cannot prove honesty or eliminate flakiness. The non-atomic mutant and any shared-writer race control require measurement before their claims can be called detected. Generated certificates change shape and identify their control execution and remaining gaps.
