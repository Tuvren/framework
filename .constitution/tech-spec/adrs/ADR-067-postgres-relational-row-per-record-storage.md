### ADR-067 PostgreSQL Backend Storage Is Relational Row-Per-Record (Postgres-Only Supersession of ADR-066's Blob Retention)

- **Status:** accepted.
- **Context:**
  - ADR-066 recorded that issue #108 optimized the *operational* layer around the blob-per-scope storage model without changing physical storage shape: postgres still kept one canonical-CBOR snapshot row per Scope; residual write cost remained O(blob) because ~90–96% of encode at 10,000 objects is canonical-CBOR of the whole twelve-family snapshot. ADR-066 explicitly did **not** decide `SPK-BK007`'s Option B (row-per-record redesign); it established the optimized-blob baseline that redesign must beat.
  - Issue #110 opens that redesign **for the PostgreSQL backend only**. Evidence that the current Postgres package is a forked in-memory backend with a serialize-the-whole-Scope dump: seven of ten source files under `typescript/kernel/backends/postgres/src/lib/` are `memory-backend-*.ts`, and the only physical table is `backend_postgres_snapshots(snapshot_id, scope, snapshot_cbor BYTEA, …)`.
  - The SQLite backend already ships the target data model: one table per record family, one row per item, foreign keys, targeted write-set validation, deferred FKs for reclaim (`typescript/kernel/backends/sqlite/migrations/`). Postgres was supposed to be a second persistent *relational* backend; it forked the memory prototype instead.
  - Acceptance criteria (issue #110): family tables with FKs and no live single-blob snapshot column; writes proportional to the delta; leaf hashes/wire bytes unchanged vs memory; open-time migration of existing blob databases without state loss.
- **Decision:**
  1. **The PostgreSQL backend's physical storage model is row-per-record relational.** One table per record family (`objects`, `schemas`, `turn_trees`, `turn_tree_paths`, `ordered_path_chunks`, `turn_nodes`, `threads`, `branches`, `turns`, `runs`, `staged_results`, `observe_annotations`) plus validation support tables (`turn_node_lineage_roots` and the SQLite-equivalent indexes). Live operational state is not stored as a single `snapshot_cbor` cell per Scope.
    - **Amendment (2026-07-28, PR #111 round-3 review):** Round-3 review found a real storable-text gap this decision's family tables inherit from choosing PostgreSQL `text` columns for every caller-supplied identifier and text field. The kernel contract treats identifiers (`threadId`, `branchId`, `turnId`, `runId`, `taskId`, `schemaId`, and similar) as opaque non-empty strings with no reserved codepoints, and the memory backend accepts any such string, including one containing U+0000 — but a PostgreSQL `text` column cannot store a NUL byte at all, so a caller-supplied value containing U+0000 would otherwise reach the write boundary and fail with a raw, backend-specific engine error instead of a typed one. The relational schema therefore constrains caller-supplied identifier/text fields to PostgreSQL-storable text (no U+0000); the backend validates this at the write boundary and rejects a violation with a typed `postgres_backend_unstorable_text` error rather than letting a raw engine error surface. This is a documented, intentional divergence from the memory backend's accept-anything behavior — a PostgreSQL storage-engine limitation surfaced honestly at the boundary, not a change to the kernel's opaque-string contract, which otherwise still treats identifiers as arbitrary non-empty strings.
    - **Amendment (2026-07-29, PR #111 round-5 review):** Round-5 review found that the storable-text write-boundary check the amendment above describes does not, and structurally cannot, extend to every read surface that accepts the same identifier fields back for a lookup. `threads.get`, `threads.list`'s cursor/filter identifiers, `runs.get`, `stagedResults.get`, and `observeAnnotations.listByRun` all pass a caller-supplied identifier straight into a `WHERE ... = $n` comparison against the same PostgreSQL `TEXT` column class the write boundary constrains, with no read-side storable-text guard of their own; a lookup identifier containing U+0000 therefore reaches the wire and surfaces the same typed generic `postgres_backend_engine_error` a raw invalid-byte-sequence failure produces, rather than fabricating the family's own null/not-found miss. This is an accepted, documented divergence from the memory and SQLite backends, which both treat an unrecognized identifier — including one no PostgreSQL `TEXT` column could ever have stored — as an ordinary miss and return `null`/empty. The divergence is judged safe, not merely tolerated, because kernel-committed state can never contain such an identifier in the first place: the write boundary the amendment above describes rejects a U+0000-bearing identifier before it is ever persisted, so a read-side probe for one is inherently a probe for a record that provably does not and cannot exist under this backend — surfacing the storage engine's own honest rejection of the probe value is preferred here over fabricating a miss result for a query PostgreSQL cannot actually execute as asked.
    - **Amendment (2026-07-29, PR #111 round-6 review):** Round-6 review found a second, independent PostgreSQL-specific text limit the storable-text guard above left unaddressed: btree index row size. PostgreSQL caps a single btree index tuple at 2704 bytes on the default 8 KB page size (`ERROR: index row size ... exceeds btree version 4 maximum 2704`, SQLSTATE 54000), and every family table in `migrations/0001_relational_schema.sql` puts caller-supplied identifiers directly into `(scope, ...)` primary keys and the 21 `idx_*` indexes, so a sufficiently long, incompressible identifier previously reached the write boundary and failed with the same untyped `postgres_backend_engine_error` the amendments above were written to eliminate — confirmed against a live devenv instance, where an incompressible ~3.8KB identifier in a `(scope, thread_id)` primary key produced exactly that error — while the memory and SQLite backends, which carry no btree index-row limit, accept the identical value. `assertPostgresStorableText` now also rejects a value whose UTF-8 byte length exceeds 512 bytes with a distinct typed `postgres_backend_text_too_long` error (naming the field, its actual byte length, and the bound), applied at the same write boundary as the NUL check above with no call-site changes, since every caller-supplied field already routed through that guard inherits the length check for free. 512 bytes per field was chosen, not engineered to the 2704 ceiling: it is sized off the largest verified index-row composite in the schema, `idx_turns_scope_thread_branch_head_turn_node`'s three bounded columns plus one fixed 64-byte content hash (3×512+64 = 1600 raw bytes, ~1650 with btree/varlena overhead, over 1000 bytes of headroom under 2704), with the `observe_annotations` `(scope, record_key)` primary key — the field the round-6 finding centered on, since `record_key` (see `keyObserveAnnotation`/`nextObserveAnnotationRecordKey` in `postgres-state-utils.ts`) length-prefixes and concatenates runId, createdAtMs, annotationHash, and turnNodeHash into a single column — as the second governing case (1199 raw bytes at the same bound, smaller than the turns composite only because two of its four packed fields are kernel content hashes fixed at exactly 64 lowercase hex characters rather than caller-bounded text). This is an accepted, documented divergence from the memory and SQLite backends: real kernel identifiers are hashes/UUIDs well under 100 bytes, so the bound is a divergence-honesty backstop against pathological caller input, not a constraint any legitimate identifier is expected to approach, and both worst-case composites were verified to insert successfully with their bounded fields held at the 512-byte limit.
  2. **Scope isolation remains row-level in a shared host-chosen PostgreSQL schema (ADR-048/049).** Every family table includes `scope TEXT NOT NULL` in its primary key and foreign keys so multi-Scope hosts that share one `schemaName` keep construction-bound isolation. This is **not** schema-per-scope and **not** SQLite's file-per-scope realization — only the *family* shape is mirrored from SQLite.
    - **Amendment (2026-07-29, PR #111 round-5 review):** Round-5 review recorded a schema-naming default change alongside this decision: the backend-owned default schema name changes from `public` to `tuvren_kernel`. The relational redesign this ADR decided replaced a single opaque `snapshot_cbor` blob table with thirteen generically-named family and support tables (`objects`, `schemas`, `turn_trees`, `turn_tree_paths`, `ordered_path_chunks`, `turn_nodes`, `threads`, `branches`, `turns`, `runs`, `staged_results`, `observe_annotations`, `turn_node_lineage_roots`) living directly in whatever schema a host points the backend at; defaulting that to Postgres's own `public` schema meant an unconfigured host's default installation could collide with unrelated application tables sharing common generic names, and — more sharply — that `destroyPostgresBackend`'s `DROP SCHEMA ... CASCADE` teardown path could destroy a host's own `public`-schema tables if ever invoked against a default-configured instance. `tuvren_kernel` removes both hazards from the unconfigured default without changing the construction-time override a host may still supply.
  3. **Write and maintenance paths match the post-#108 SQLite operational semantics, adapted for Postgres:**
     - `transact()` applies targeted per-record SQL and re-validates the write set before `COMMIT` (not a whole-Scope re-encode).
     - Foreign keys are `DEFERRABLE INITIALLY DEFERRED` so reclaim can delete in dependency-friendly order and still fail commit on broken survivors (SQLite's `defer_foreign_keys = ON` equivalent).
     - `health()` remains a liveness/coherence probe; `fsck()` remains explicit full validation; `reclaim()` remains single-load with a targeted survivor check.
    - **Amendment (2026-07-29, PR #111 round-5 review):** Round-5 review clarified which artifact backs which claim in this decision's delta-proportional write-cost story. Issue #110's Gherkin scenario about flat marginal single-object write latency — that writing one more object costs the same regardless of how many objects already share the Scope — is evidenced by ungated bench numbers (`bench/postgres-write-latency.bench.ts`), run for measurement and regression-watching but not wired into a pass/fail gate. The gated automated check path that actually enforces this decision's delta-proportional claim is the structural `xmin` row-touch proof (`test/backend-postgres.delta-write.test.ts`): a single-object write touches exactly one row across the whole relational schema, verified by reading back which rows carry the write transaction's own `xmin`, regardless of how many pre-existing rows already share the Scope. The structural proof is the gate, deliberately, because a wall-clock latency assertion would be flaky in CI; the bench numbers remain the human-facing evidence of the latency claim itself.
  4. **Leaf encoding authority is unchanged.** Canonical-CBOR of individual kernel records, content hashes, and the `RuntimeBackend` contract shape are preserved (ADR-008/010/011). This ADR changes only physical layout and write granularity for `@tuvren/backend-postgres`.
  5. **Existing blob-per-scope databases migrate on open.** Opening a database that still has `backend_postgres_snapshots` explodes each Scope's snapshot into relational rows once under an advisory lock, then retires the blob table. No committed logical state may be lost or hash-altered.
  6. **Supersession scope:** Decision (1) of ADR-066 ("the blob-per-scope storage model is retained") is **superseded for `@tuvren/backend-postgres` only**. ADR-066 remains the historical record of issue #108's operational optimizations and residual-cost measurements; those measurements are the regression baseline the relational backend must beat. SQLite and memory backends are unaffected by this ADR. Shared invariant logic continues to live in `@tuvren/backend-shared`; the Postgres package must not re-fork the memory backend for persistence.
    - **Amendment (2026-07-28, PR #111 round-2 review):** "SQLite and memory backends are unaffected by this ADR" is narrowed, not reversed, by how the preceding sentence's shared-invariant-logic requirement was actually carried out. Giving Postgres shared invariant logic in `@tuvren/backend-shared` meant lifting the state-validation, integrity-assertion, run-invariant, and reclamation logic that used to be SQLite-owned into shared factories, and rewriting the corresponding SQLite modules (for example `sqlite-state-validation.ts`, `sqlite-integrity-assertions.ts`, `sqlite-run-invariants.ts`, `sqlite-reclamation.ts`) into thin shims that delegate to those factories. This is a mechanical restructuring with zero behavioral change — SQLite's public contract, physical schema, and hashes are untouched and its test suite is green throughout — so the sentence's substance (no semantic or schema effect on SQLite) still holds; only its literal claim that SQLite source files are untouched does not. The memory backend was not part of this refactor: `@tuvren/backend-memory`'s `memory-backend-*.ts` modules still duplicate the same invariant logic locally rather than sourcing it from `@tuvren/backend-shared`. That remaining duplication is recorded as a follow-up below, not resolved by this ADR.
- **Consequences:**
  - `@tuvren/backend-postgres` gains checked-in SQL migrations and a SQLite-shaped module layout (lookups, repositories, write tracker, transaction validation, lineage helpers). The seven `memory-backend-*.ts` forks and the whole-snapshot encode/decode hot path are removed as the redesign lands.
  - Issue #108's A3 content-hash decode memoization of the whole snapshot is no longer the write-path design center for Postgres (it was a blob-shape mitigation). The blob-era phase vocabulary (`decode`, `encode`, `hash`, and the undifferentiated `validate`) this decision's original text referenced is retired along with the storage model that emitted it; `PersistencePhase` (`typescript/kernel/backends/shared/src/lib/backend-invariant-phase-observer.ts`) now carries only the row-per-record vocabulary shared with SQLite (`load`, `lock-wait`, `write`, `validate-loaded`, `validate-lineage-index`, `validate-committed`, `validate-reclaim-survivors`, `validate-write-set`) plus Postgres's own `blob-migration` phase for the one-time open-time explode (decision 5). Phase observers attribute costs against that live vocabulary at row granularity, not against the retired blob-era names.
  - **Pre-1.0 type-level narrowings shipped at 0.1.0:** because no per-PR changeset convention exists yet in this repository, the intentional breaking type-level removals this PR ships are recorded here rather than left implicit. `PersistencePhase`'s four blob-era members (`decode`, `encode`, `hash`, `validate`) are removed, not deprecated — no backward-compatible union member is retained. `@tuvren/backend-postgres`'s `SnapshotCacheObserver` type export and the `PostgresBackendOptions.snapshotCacheObserver` construction option (issue #108 M3's whole-snapshot decode-memoization observability seam) are removed entirely, since the row-per-record redesign has no whole-snapshot decode step left to observe.
  - Hosts and operators: a database written by the pre-#110 blob backend is upgraded automatically on first open with a package that implements this ADR; downgrade is not supported.
  - `data-models/README.md` §3.5 (or equivalent Postgres storage pointer) must describe family tables + scope partition, not `snapshot_cbor` as live state.
  - Conformance and package tests remain the behavioral oracle; no wire or hash fixtures change solely because of this ADR.
  - Follow-ups left open: true multi-writer concurrency *inside* one Scope (v1 keeps same-scope serialization, matching SQLite single-writer-per-file); sharing SQL DDL between SQLite and Postgres via a generator; folding `@tuvren/backend-memory`'s still-duplicated state-validation, integrity-assertion, run-invariant, and reclamation logic onto the same `@tuvren/backend-shared` factories SQLite now shims over (see the decision-6 amendment above).
