### ADR-067 PostgreSQL Backend Storage Is Relational Row-Per-Record (Postgres-Only Supersession of ADR-066's Blob Retention)

- **Status:** accepted.
- **Context:**
  - ADR-066 recorded that issue #108 optimized the *operational* layer around the blob-per-scope storage model without changing physical storage shape: postgres still kept one canonical-CBOR snapshot row per Scope; residual write cost remained O(blob) because ~90–96% of encode at 10,000 objects is canonical-CBOR of the whole twelve-family snapshot. ADR-066 explicitly did **not** decide `SPK-BK007`'s Option B (row-per-record redesign); it established the optimized-blob baseline that redesign must beat.
  - Issue #110 opens that redesign **for the PostgreSQL backend only**. Evidence that the current Postgres package is a forked in-memory backend with a serialize-the-whole-Scope dump: seven of ten source files under `typescript/kernel/backends/postgres/src/lib/` are `memory-backend-*.ts`, and the only physical table is `backend_postgres_snapshots(snapshot_id, scope, snapshot_cbor BYTEA, …)`.
  - The SQLite backend already ships the target data model: one table per record family, one row per item, foreign keys, targeted write-set validation, deferred FKs for reclaim (`typescript/kernel/backends/sqlite/migrations/`). Postgres was supposed to be a second persistent *relational* backend; it forked the memory prototype instead.
  - Acceptance criteria (issue #110): family tables with FKs and no live single-blob snapshot column; writes proportional to the delta; leaf hashes/wire bytes unchanged vs memory; open-time migration of existing blob databases without state loss.
- **Decision:**
  1. **The PostgreSQL backend's physical storage model is row-per-record relational.** One table per record family (`objects`, `schemas`, `turn_trees`, `turn_tree_paths`, `ordered_path_chunks`, `turn_nodes`, `threads`, `branches`, `turns`, `runs`, `staged_results`, `observe_annotations`) plus validation support tables (`turn_node_lineage_roots` and the SQLite-equivalent indexes). Live operational state is not stored as a single `snapshot_cbor` cell per Scope.
    - **Amendment (2026-07-28, PR #111 round-3 review):** Round-3 review found a real storable-text gap this decision's family tables inherit from choosing PostgreSQL `text` columns for every caller-supplied identifier and text field. The kernel contract treats identifiers (`threadId`, `branchId`, `turnId`, `runId`, `taskId`, `schemaId`, and similar) as opaque non-empty strings with no reserved codepoints, and the memory backend accepts any such string, including one containing U+0000 — but a PostgreSQL `text` column cannot store a NUL byte at all, so a caller-supplied value containing U+0000 would otherwise reach the write boundary and fail with a raw, backend-specific engine error instead of a typed one. The relational schema therefore constrains caller-supplied identifier/text fields to PostgreSQL-storable text (no U+0000); the backend validates this at the write boundary and rejects a violation with a typed `postgres_backend_unstorable_text` error rather than letting a raw engine error surface. This is a documented, intentional divergence from the memory backend's accept-anything behavior — a PostgreSQL storage-engine limitation surfaced honestly at the boundary, not a change to the kernel's opaque-string contract, which otherwise still treats identifiers as arbitrary non-empty strings.
  2. **Scope isolation remains row-level in a shared host-chosen PostgreSQL schema (ADR-048/049).** Every family table includes `scope TEXT NOT NULL` in its primary key and foreign keys so multi-Scope hosts that share one `schemaName` keep construction-bound isolation. This is **not** schema-per-scope and **not** SQLite's file-per-scope realization — only the *family* shape is mirrored from SQLite.
  3. **Write and maintenance paths match the post-#108 SQLite operational semantics, adapted for Postgres:**
     - `transact()` applies targeted per-record SQL and re-validates the write set before `COMMIT` (not a whole-Scope re-encode).
     - Foreign keys are `DEFERRABLE INITIALLY DEFERRED` so reclaim can delete in dependency-friendly order and still fail commit on broken survivors (SQLite's `defer_foreign_keys = ON` equivalent).
     - `health()` remains a liveness/coherence probe; `fsck()` remains explicit full validation; `reclaim()` remains single-load with a targeted survivor check.
  4. **Leaf encoding authority is unchanged.** Canonical-CBOR of individual kernel records, content hashes, and the `RuntimeBackend` contract shape are preserved (ADR-008/010/011). This ADR changes only physical layout and write granularity for `@tuvren/backend-postgres`.
  5. **Existing blob-per-scope databases migrate on open.** Opening a database that still has `backend_postgres_snapshots` explodes each Scope's snapshot into relational rows once under an advisory lock, then retires the blob table. No committed logical state may be lost or hash-altered.
  6. **Supersession scope:** Decision (1) of ADR-066 ("the blob-per-scope storage model is retained") is **superseded for `@tuvren/backend-postgres` only**. ADR-066 remains the historical record of issue #108's operational optimizations and residual-cost measurements; those measurements are the regression baseline the relational backend must beat. SQLite and memory backends are unaffected by this ADR. Shared invariant logic continues to live in `@tuvren/backend-shared`; the Postgres package must not re-fork the memory backend for persistence.
    - **Amendment (2026-07-28, PR #111 round-2 review):** "SQLite and memory backends are unaffected by this ADR" is narrowed, not reversed, by how the preceding sentence's shared-invariant-logic requirement was actually carried out. Giving Postgres shared invariant logic in `@tuvren/backend-shared` meant lifting the state-validation, integrity-assertion, run-invariant, and reclamation logic that used to be SQLite-owned into shared factories, and rewriting the corresponding SQLite modules (for example `sqlite-state-validation.ts`, `sqlite-integrity-assertions.ts`, `sqlite-run-invariants.ts`, `sqlite-reclamation.ts`) into thin shims that delegate to those factories. This is a mechanical restructuring with zero behavioral change — SQLite's public contract, physical schema, and hashes are untouched and its test suite is green throughout — so the sentence's substance (no semantic or schema effect on SQLite) still holds; only its literal claim that SQLite source files are untouched does not. The memory backend was not part of this refactor: `@tuvren/backend-memory`'s `memory-backend-*.ts` modules still duplicate the same invariant logic locally rather than sourcing it from `@tuvren/backend-shared`. That remaining duplication is recorded as a follow-up below, not resolved by this ADR.
- **Consequences:**
  - `@tuvren/backend-postgres` gains checked-in SQL migrations and a SQLite-shaped module layout (lookups, repositories, write tracker, transaction validation, lineage helpers). The seven `memory-backend-*.ts` forks and the whole-snapshot encode/decode hot path are removed as the redesign lands.
  - Issue #108's A3 content-hash decode memoization of the whole snapshot is no longer the write-path design center for Postgres (it was a blob-shape mitigation). Phase observers may still attribute load/encode/write/lock-wait costs at row granularity.
  - Hosts and operators: a database written by the pre-#110 blob backend is upgraded automatically on first open with a package that implements this ADR; downgrade is not supported.
  - `data-models/README.md` §3.5 (or equivalent Postgres storage pointer) must describe family tables + scope partition, not `snapshot_cbor` as live state.
  - Conformance and package tests remain the behavioral oracle; no wire or hash fixtures change solely because of this ADR.
  - Follow-ups left open: true multi-writer concurrency *inside* one Scope (v1 keeps same-scope serialization, matching SQLite single-writer-per-file); sharing SQL DDL between SQLite and Postgres via a generator; folding `@tuvren/backend-memory`'s still-duplicated state-validation, integrity-assertion, run-invariant, and reclamation logic onto the same `@tuvren/backend-shared` factories SQLite now shims over (see the decision-6 amendment above).
