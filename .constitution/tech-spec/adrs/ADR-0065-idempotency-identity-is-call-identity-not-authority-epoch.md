### ADR-0065 The Idempotency Identity Is the Logical Call Identity, Not the Execution Attempt

- **Status:** accepted. Amends ADR-0052 §1.
- **Context:**
  - ADR-0052 §1 promises that "a re-dispatch after recovery presents the **same identity** for the same logical call," and derives that identity from `(runId, callId, fencingToken)`. The architecture layer repeats the promise as the reason the envelope exists: the dispatch envelope carries an idempotency identity "so a client environment can deduplicate a side effect it re-executes after a reconnect" (`.constitution/architecture/containers.md`, Client Endpoint Boundary).
  - **Two of the three components are not stable for one logical call, so the promise never held.**
    - The **fencing token** rotates on every lease renewal: `createFencingToken()` mints a fresh token on each renew (`typescript/kernel/runtime/src/lib/runtime-kernel-runs.ts:542`), `ActiveRunLease.fencingToken` is documented as rotating (`typescript/runtime/src/lib/runtime-core-liveness.ts:44-45`) and is overwritten on every renewal and piggybacked step result (`:206`).
    - The **`runId`** is less stable still, and this is the more damaging half. A Run is one execution *attempt*, not the interaction: the kernel spec states that "multiple Runs may serve the same Turn (pause/resume creates new Run from pause point)" (§5.2) and that a replacement execution after preemption "MUST be a new Run. Reopening the stale Run is illegal" (§5.2). The framework mints one per **ReAct iteration** (`typescript/runtime/src/lib/runtime-core-iteration.ts:579`, stamped onto the batch environment at `:718`), per approval resume (`typescript/runtime/src/lib/runtime-core-tool-resume.ts:176`), and at each recovery. The identity therefore churned in a perfectly healthy loop, not merely across the failures the envelope exists to survive.
  - The result was an idempotency key that changed under exactly the conditions it was supposed to be invariant to, which makes it worse than no key: a peer or tool that trusted it for external dedup would fail to dedup precisely on retry, resume, and recovery.
  - **Existing verification certified the defect rather than the contract.** `typescript/runtime/test/idempotency-identity.test.ts` asserts that changing only the fencing token yields a *different* key — a true statement about the function and an irrelevant one about the promise — and its own comment concedes that "in real preemption recovery the runtime mints a fresh runId ... so the live triple is not stable across recovery," deferring reconciliation elsewhere. No test anywhere drives a real pause/resume or recovery and asserts the key is unchanged across it.
  - The gap surfaced while reviewing ADR-0063 (issue #102), whose reattach-and-redelivery design leans on the envelope for at-most-once *effect*. The first design to depend on the guarantee immediately depended on it incorrectly, which is the strongest possible argument that the guarantee needed to become real rather than be worked around.
- **Decision:**
  1. **The idempotency identity is derived from `(turnId, callId)`** — the logical call identity. `deriveIdempotencyKey(turnId, callId)` replaces the `(runId, callId, fencingToken)` triple. The canonical injective JSON-array encoding and the sha256 hex digest are unchanged, so the value remains a fixed-length opaque token suitable for presenting to an external system.
  2. **This is the minimal tuple that is both stable and unique.** `turnId` identifies the user-visible interaction unit, which is precisely the scope designed to span many Runs, and every resume and recovery path threads the existing `handle.turnId` through unchanged (`runtime-core-tool-resume.ts:181`, `:532`; recovery returns the pre-existing `turnId` read back from the kernel's expired-run record, `runtime-core-expired-recovery.ts:154`). `callId` is framework-generated exactly once when the assistant's tool-call part is first parsed (`typescript/runners/react/src/lib/react-runner-stream-support.ts:493`) and never re-minted; recovery re-presents it from committed or staged state, a stability that skip-completed-by-`callId` recovery already depends on (framework spec §4.9, §8.6). `(threadId, callId)` would also be stable but is a looser scope than necessary, since a thread spans many turns and forked branches.
  3. **The fencing token's role is unchanged and unshared: it is write authority, never identity.** ADR-0052 §3 (client-result-as-proposal — a result becomes durable only through a commit under a valid run fencing token) is untouched and remains the mechanism that stops a stale owner mutating committed history. The defect was *conflation*: "which logical call is this?" and "may I commit this?" are orthogonal questions, and answering the first with the answer to the second made the first unstable for exactly as long as the second was doing its job. Keying on `runId` compounded it by answering the first question with "which attempt is this?" instead.
  4. **The guarantee is stated in terms an external system can act on, and scoped to what actually holds.** The envelope guarantees that every dispatch of one logical call presents an identical key across the first attempt, a framework retry, re-dispatch on a later ReAct iteration, re-dispatch after an approval resume, ADR-0063 redelivery after a reconnect, and cold preemption recovery of an interrupted tool batch. Framework specification §4.9 requires the replacement Run to reconstruct the original assistant tool calls from durable state, match completed results by `callId`, and redispatch every missing call with its original `(turnId, callId)` identity. The replacement Run does this without invoking the runner for the recovered iteration or staging another copy of the assistant message. This rule includes a missing call marked `nonRetryable`: that flag stops the live owner from retrying after authority loss, but it does not let cold recovery omit an unresolved logical call.
     The envelope does not guarantee that an external effect occurs once. The tool, peer, or external system must use the presented key to deduplicate the effect. The framework guarantees stable key presentation and fenced durable commits; it cannot determine whether an unreported external attempt completed.
  5. **Verification asserts the contract across the paths that can change execution attempts.** The unit tests over `createToolExecutionContext` prove that one `(turnId, callId)` pair keeps one key across different Run and fencing identities. KRT-CR003 exercises cold recovery against durable runtime state, and KRT-CR005 promotes the missing-call and key-preservation behavior into shared conformance. KRT-CR006 drives a real approval pause and resume and proves that the resumed dispatch retains the original Turn and call identity under a different `runId`. These checks verify dispatch identity and durable recovery behavior. They do not execute or certify an external system's deduplication logic.
- **Consequences:**
  - ADR-0052 §1's identity promise holds for retry, iteration re-dispatch, approval resume, ADR-0063 redelivery, and cold recovery of an interrupted tool batch. Hosts and tools can rely on stable presentation for those paths, but the external system must deduplicate the presented key to make the effect occur once.
  - **Both implementation obligations are closed with behavioral evidence.**
    1. *Cold preemption recovery preserves call identity.* The runtime proof in `typescript/runtime/test/runtime-core.recovery.test.ts` dispatches only the missing `nonRetryable` call, retains its original `callId`, derives its original key, and leaves one copy of the original assistant message. The KRT-CR003 records are `.constitution/evidence/KRT-CR003/verification-summary.md` and `.constitution/evidence/KRT-CR003/live-probe.log`. Shared conformance adds `runtime-lifecycle-ext.stale-recovery.interrupted-batch-skips-runner`, `runtime-lifecycle-ext.stale-recovery.interrupted-batch-dispatches-missing-set`, and `runtime-lifecycle-ext.stale-recovery.interrupted-batch-preserves-idempotency-keys`. The KRT-CR005 result is recorded in `.constitution/evidence/KRT-CR005/m5-conformance-summary.md`. The preemption head is independently covered by `kernel.run-liveness.stale_preemption`.
    2. *Approval resume preserves the Turn identity across Runs.* `typescript/runtime/test/runtime-core.approval-basics.test.ts` drives an approval request through `resolveApproval(...)`. It proves that the dispatch keeps the original `turnId` and `callId`, derives the key from that pair, and uses a `runId` different from the paused Run. The KRT-CR006 result is recorded in `.constitution/evidence/KRT-CR006/approval-resume-summary.md`.
  - **No durable-state or wire migration.** The key is never persisted: it is derived per dispatch and handed to `ToolExecutionContext.idempotencyKey` and `ClientInvocationEnvelope.idempotencyKey` (`spec/host/session/typespec/main.tsp`), both of which keep an unchanged `string` shape. Emitted *values* change, which is visible only to an external system mid-flight across the upgrade — accepted, since the values being replaced were never stable enough to be relied on.
  - **Behavior change worth naming:** a framework retry of the same `callId`, and every iteration of a loop that re-dispatches it, now present the same key as the original attempt, where previously each attempt could differ. That is the intended semantic — a retry of a logical call *should* dedup against the attempt that may already have succeeded externally — and is the whole reason a caller presents an idempotency key.
  - **Trade-off recorded:** `(turnId, callId)` deliberately does not distinguish attempts, so a host that wants per-attempt external identity (for example to record each try separately) cannot recover it from this key. That is the correct default for a *dedup* key; per-attempt observability belongs to telemetry and the `tool.audit` trail, which already carry attempt-level detail.
  - The optional-fencing-token branch and its absent-versus-empty-string normalization disappear with the parameter. A runtime with run-liveness leases and one without now derive identity identically, which is itself the honest outcome — liveness configuration never should have changed a call's identity.
  - `docs/KrakenFrameworkSpecification.md` §4.8's side-effect-once rule is amended in the same change, since it also stated the `(runId, callId, fencingToken)` triple.
