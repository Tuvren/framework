### ADR-0083 Codegen-Free Schema Validation and Clean Tool-Admission Failure

- **Status:** accepted. Amends ADR-0038, so that a wrapped or bare JSON Schema with no host validator is validated by the runtime validator instead of being accepted unchecked. Amends ADR-0039, so that MCP tool input is validated by the runtime validator rather than Ajv.
- **Context:** Measured on the published 0.3.0 packages and on master. The reproduction ran Node v24 with `--disallow-code-generation-from-strings`, the memory backend, a scripted provider, and one tool with a plain JSON Schema.
  - **Bug 1, the reported error is wrong.** `awaitResult()` reports `memory_backend_active_run_turn_head_mismatch` while the event stream carries the real `EvalError`. The next turn on that branch fails with `kernel_runtime_turn_parent_start_mismatch`. The same thing happens without the flag for any exception during tool admission, such as an unresolvable `$ref` or an `approval()` predicate that throws.
  - **Cause of bug 1, part A.** `failTrackedRunWithoutBranchAdvance` (`typescript/runtime/src/lib/runtime-core-turn-progress.ts:206-219`) calls `run.complete(failed)`. Per kernel specification §5.6, that call reactively checkpoints the staged assistant tool-call batch and moves both the branch head and the turn head. The function then resets only the branch head, although its documentation says failed iteration work is not observable on the branch.
  - **Cause of bug 1, part B.** Finalization then opens a Run whose turn-head lineage the backend invariant rejects. `publishProjectedError` (`runtime-core-events.ts:345-353`) overwrites the remembered error for both fatal and non-fatal errors, so the result reports the later backend error.
  - **Bug 2, validation needs code generation.** Ajv 8.18.0 generates code on every compile (`ajv/dist/compile/index.js:89`) and has no interpreter mode. Four production packages compile Ajv at runtime: runtime tool validation (`tool-execution-validation.ts:24,41,50`), ReAct structured output (`typescript/runners/react/src/lib/react-runner.ts:643-675`), MCP tool input (`typescript/tools/mcp-client/src/lib/mcp-tool-source.ts:335,556`), and the AI SDK bridge's structured output (`typescript/providers/bridge-ai-sdk/src/lib/ai-sdk-provider-bridge.ts:893-904`). All four therefore fail on runtimes that forbid code generation, including runtimes under a content security policy and isolate runtimes. Standalone precompilation cannot cover schemas that arrive at runtime, and MCP tool schemas always arrive at runtime.
  - **Bug 3, a helper silently skips validation.** `defineTool` with a plain JSON Schema, and `jsonSchema(schema)` without `validate`, build a `validate()` that accepts any input (`typescript/sdk/src/lib/schema-authoring.ts:242-256,389-392`). This happens on every runtime, while the native path validates. A plain JSON `outputSchema` on a no-codegen runtime becomes an `isError` result carrying the raw `EvalError`, after the tool has already run. A failed structured-output schema compile drops its `details`.
  - **No existing rule.** The framework specification has no rule on whether failed iteration work is visible. The `details` shape of a validation failure is not fixed by any authority artifact under `spec/`.
- **Decision:**
  1. **One codegen-free validator.** A single interpreting JSON Schema validator, which never generates code, validates tool input, tool output, MCP tool input, and structured output in the ReAct runner and the AI SDK bridge, on every runtime. It covers drafts 7, 2019-09, and 2020-12, which the runner and bridge already select by `$schema`. Ajv leaves `@tuvren/runtime`, `@tuvren/runner-react`, `@tuvren/mcp-client`, and `@tuvren/provider-bridge-ai-sdk`, and no production package keeps a second validation path. Testkits and conformance tooling are not production packages. The selected candidate is `@cfworker/json-schema` 4.1.1: MIT licensed, ES modules only, no dependencies, and no `Function` or `eval` in the package. EPIC-DM's spike must confirm draft coverage, `$ref` resolution, format behavior, and a stable `details` projection under `--disallow-code-generation-from-strings` before adoption. If it fails, the spike proposes another interpreting validator and the owner rules. The validator's npm scope names a hosting vendor, but the library is runtime-neutral. Tuvren adds no vendor-specific code path, flag, or terminology.
  2. **Schemas are checked at registration.** A plain JSON Schema is checked when the tool, MCP tool source, or structured-output request is registered. An invalid schema, or an unresolvable reference, fails there with a typed error (`tool_schema_invalid`) instead of during a turn.
  3. **The helpers use the same validator.** `defineTool` and `jsonSchema` route a JSON Schema without a host validator through the runtime validator. A host validator (`CustomSchema`, `jsonSchema(schema, { validate })`, Zod, or Standard Schema) still takes precedence, so CAP-040's no-lock-in requirement holds.
  4. **Failed iteration work is never observable.** When an iteration fails hard, the branch head and the turn head return to the stable head in one kernel transaction, and later turns on the branch start cleanly. EPIC-DM's spike decides whether the existing syscalls can do this atomically or a kernel operation is needed. A new kernel operation goes through the kernel authority packet and plans first, under the CLAUDE.md authority rules. The framework specification gains this rule.
  5. **The root cause wins.** An execution result reports the first fatal error as its error. A later finalization failure is attached as a secondary cause and never replaces the root cause. The event stream continues to carry both.
  6. **The failure path is certified.** Engine conformance gains checks, judged by the runner from observations, that a tool-admission failure reports its root cause, leaves the branch usable for the next turn, and leaves no failed iteration work in branch history. A portability lane runs runtime validation under `--disallow-code-generation-from-strings`.
  7. **Breaking changes are released as breaking.** The validation-failure `details` shape follows the new validator's projection, and tools whose input previously went unvalidated through the SDK helpers now reject invalid input. Both are breaking changes to untagged behavior and ship in a minor release under ADR-0069 decision 3, without a compatibility path.
- **Alternatives considered:**
  - Keep Ajv and fail at registration with a typed error on no-codegen runtimes. Rejected by the owner: plain JSON Schema and MCP tools would stay unusable on those runtimes.
  - Add a pluggable validator option and keep Ajv as the default. Rejected by the owner: the default would stay broken on those runtimes unless each host opted in.
  - Detect whether code generation is available and fall back to an interpreter. Rejected: two validators give two semantics for one schema.
  - Keep failed iteration work visible as reactive-checkpoint lineage. Rejected by the owner: it contradicts the documented intent and leaves orphan tool calls in durable reads.
  - Other interpreting validators surveyed by reading their packages only, without installing or running them:
    - `@hyperjump/json-schema` 1.18.0: drafts 04 to 2020-12, seven dependencies; the fallback candidate.
    - `jsonschema` 1.5.0: draft-07 at most.
    - `@exodus/schemasafe` 1.3.0: generates code with `Function`, so it was ruled out.
  - No second independent design was requested. The owner ruled the scope in the session, and the library choice is confirmed by spike.
- **Consequences:** These are assumed until observed.
  - Tools with a plain JSON Schema, including MCP tools, work on runtimes that forbid code generation.
  - A bad schema fails at registration.
  - A tool-admission failure reports its real cause and leaves the branch usable.
  - Validation performance on large schemas may be lower than Ajv's compiled code. Tool schemas are small, and the spike records a measurement.
  - The conformance verifier keeps precompiled Ajv (ADR-0082 decision 4), so the verifier and production do not share one validator's blind spots.
  - `@tuvren/runtime`, `@tuvren/runner-react`, `@tuvren/sdk`, `@tuvren/mcp-client`, and `@tuvren/provider-bridge-ai-sdk` change behavior and need changesets.
