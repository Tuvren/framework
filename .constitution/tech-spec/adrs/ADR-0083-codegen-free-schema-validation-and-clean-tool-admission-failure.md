### ADR-0083 Codegen-Free Schema Validation and Clean Tool-Admission Failure

- **Status:** accepted. Amends ADR-0038, so that a wrapped or bare JSON Schema with no host validator is validated by the runtime validator instead of being accepted unchecked. Amends ADR-0039, so that MCP tool input and output are validated by the runtime validator rather than Ajv.
- **Context:** The fact check, investigation, reproduction, and owner rulings are recorded in `.constitution/research/2026-10-29-downstream-blockers-and-owner-rulings.md`. Measured on the published 0.3.0 packages and on master. The reproduction ran Node v24 with `--disallow-code-generation-from-strings`, the memory backend, a scripted provider, and one tool with a plain JSON Schema.
  - **Bug 1, the reported error is wrong.** `awaitResult()` reports `memory_backend_active_run_turn_head_mismatch` while the event stream carries the real `EvalError`. The next turn on that branch fails with `kernel_runtime_turn_parent_start_mismatch`. The same thing happens without the flag for any exception during tool admission, such as an unresolvable `$ref` or an `approval()` predicate that throws.
  - **Cause of bug 1, part A.** `failTrackedRunWithoutBranchAdvance` (`typescript/runtime/src/lib/runtime-core-turn-progress.ts:206-219`) calls `run.complete(failed)`. In the TypeScript kernel, completing a run as failed reactively checkpoints the staged batch and moves the branch head and the turn head (`typescript/kernel/runtime/src/lib/runtime-kernel-lineage.ts:990,995`). Kernel specification sections 5.5 and 5.6 name only the branch head, and section 5.3 assigns turn-head moves to `turn.updateHead`. The function then resets only the branch head, although its documentation says failed iteration work is not observable on the branch.
  - **Cause of bug 1, part B.** Finalization then opens a Run whose turn-head lineage the backend invariant rejects. `publishProjectedError` (`runtime-core-events.ts:345-353`) overwrites the remembered error for both fatal and non-fatal errors, so the result reports the later backend error.
  - **Bug 2, validation needs code generation.** Ajv 8.18.0 generates code on every compile (`ajv/dist/compile/index.js:89`) and has no interpreter mode. Four production packages compile Ajv at runtime: runtime tool validation (`tool-execution-validation.ts:24,41,50`), ReAct structured output (`typescript/runners/react/src/lib/react-runner.ts:643-675`), MCP tool input and output (`typescript/tools/mcp-client/src/lib/mcp-tool-source.ts:335,556`), and the AI SDK bridge's structured output (`typescript/providers/bridge-ai-sdk/src/lib/ai-sdk-provider-bridge.ts:893-904`). All four therefore fail on runtimes that forbid code generation, including runtimes under a content security policy and isolate runtimes. Standalone precompilation cannot cover schemas that arrive at runtime, and MCP tool schemas always arrive at runtime.
  - **Bug 3, a helper silently skips validation.** `defineTool` with a plain JSON Schema, and `jsonSchema(schema)` without `validate`, build a `validate()` that accepts any input (`typescript/sdk/src/lib/schema-authoring.ts:242-256,389-392`). This happens on every runtime, while the native path validates. A plain JSON `outputSchema` on a no-codegen runtime becomes an `isError` result carrying the raw `EvalError`, after the tool has already run. A failed structured-output schema compile drops its `details`.
  - **No existing rule.** The framework specification has no rule on whether failed iteration work is visible. The `details` shape of a validation failure is not fixed by any authority artifact under `spec/`.
- **Decision:**
  1. **One codegen-free validator.** A single interpreting JSON Schema validator, which never generates code, validates tool input, tool output, MCP tool input and output, and structured output in the ReAct runner and the AI SDK bridge, on every runtime. It covers drafts 7, 2019-09, and 2020-12, which the runner and bridge already select by `$schema`. Ajv leaves `@tuvren/runtime`, `@tuvren/runner-react`, `@tuvren/mcp-client`, and `@tuvren/provider-bridge-ai-sdk`, and no production package keeps a second validation path. Testkits and conformance tooling are not production packages. The selected candidate is `@cfworker/json-schema` 4.1.1: MIT licensed, ships ES module and CommonJS builds, no dependencies, and no `Function` or `eval` in the package. The implementing spike must confirm draft coverage, `$ref` resolution, format behavior, and a stable `details` projection under `--disallow-code-generation-from-strings` before adoption. If it fails, the spike proposes another interpreting validator and the owner rules. The validator's npm scope names a hosting vendor, but the library is runtime-neutral. Tuvren adds no vendor-specific code path, flag, or terminology. The implementing spike chooses the wrapper’s package: a `@tuvren/core` subpath, the assumed recommendation because all consumers already depend on `@tuvren/core` and the library has no dependencies, making the validator its first runtime dependency; or per-package use of the library with the `details` projection typed in `@tuvren/core`. A patch to this ADR records the spike’s choice.
  2. **Schemas are checked before use.** Schemas declared ahead of a turn are checked at registration: tool input and output schemas, MCP tool input and output schemas when the tool source lists them, and structured-output schemas in agent configuration. A schema that first appears during a turn is checked when supplied, before the provider call that uses it; examples include a per-request `responseFormat` and a schema replaced by an around-hook (`typescript/runners/react/src/lib/react-runner-prompt.ts:369-372,479-488`, `react-runner.ts:466`). An invalid tool or MCP schema fails with typed `tool_schema_invalid`. An invalid structured-output schema fails that request with typed `structured_output_validation` and `details.reason: "schema_compilation_failed"`, and the turn fails cleanly through decisions 4 and 5. Schemas carried with a host validator (`CustomSchema`, Zod, or Standard Schema) are not checked by the built-in validator.
  3. **The helpers use the same validator.** `defineTool` and `jsonSchema` route a JSON Schema without a host validator through the runtime validator. A host validator (`CustomSchema`, `jsonSchema(schema, { validate })`, Zod, or Standard Schema) still takes precedence, so CAP-040's no-lock-in requirement holds.
  4. **Failed iteration work is never observable.** When an iteration fails hard, the branch head and the turn head return to the stable head in one kernel transaction, and later turns on the branch start cleanly. The implementing spike decides whether the existing syscalls can do this atomically or a kernel operation is needed. The implementing spike also settles whether the turn-head move inside the checkpoint is specified behavior or a kernel finding. A specification or kernel change goes through the kernel authority packet and plans first, under the CLAUDE.md authority rules. The framework specification gains this rule.
  5. **The root cause wins.** The failed branch of `ExecutionResult` (`typescript/core/src/lib/runtime-execution-contract-shapes.ts:102-112`, framework specification section 7.1) keeps `error` as the first fatal error and gains an optional `subsequentErrors: readonly TuvrenError[]` holding later failures in order. This additive optional field is a PATCH-level change under ADR-0069 decision 3; framework specification section 7.1 and `spec/host/bindings/typescript.md`, which restates the union and its `OrchestrationResult` extension, will state it. `ErrorEnvelope.cause` in `spec/core/typespec/main.tsp` keeps its meaning of underlying cause and is not reused. The event stream continues to carry both errors.
  6. **The failure path is certified.** Engine conformance gains checks, judged by the runner from observations, that a tool-admission failure reports its root cause, leaves the branch usable for the next turn, and leaves no failed iteration work in branch history. A portability lane runs runtime validation under `--disallow-code-generation-from-strings`.
  7. **Breaking changes are released as breaking.** The validation-failure `details` shape follows the new validator's projection, and tools whose input previously went unvalidated through the SDK helpers now reject invalid input. Both are breaking changes to untagged behavior and ship in a minor release under ADR-0069 decision 3, without a compatibility path. The optional `subsequentErrors` field is additive and ships at PATCH level.
- **Alternatives considered:**
  - Keep Ajv and fail at registration with a typed error on no-codegen runtimes. Rejected by the owner: plain JSON Schema and MCP tools would stay unusable on those runtimes.
  - Add a pluggable validator option and keep Ajv as the default. Rejected by the owner: the default would stay broken on those runtimes unless each host opted in.
  - Detect whether code generation is available and fall back to an interpreter. Rejected: two validators give two semantics for one schema.
  - Keep failed iteration work visible as reactive-checkpoint lineage. Rejected by the owner: it contradicts the documented intent and leaves orphan tool calls in durable reads.
  - Other interpreting validators surveyed by reading their packages only, without installing or running them:
    - `@hyperjump/json-schema` 1.18.0: drafts 04 to 2020-12, seven dependencies; the fallback candidate.
    - `jsonschema` 1.5.0: draft-07 at most.
    - `@exodus/schemasafe` 1.3.0: generates code with `Function`, so it was ruled out.
  - The owner ruled the expensive-to-reverse choices listed above. The validator library, wrapper package, and rewind mechanism were not ruled separately; they are cheap to reverse while every public package is 0.x and the owner has ruled out compatibility obligations, so no second design was commissioned and the implementing spike settles them.
- **Consequences:** These are assumed until observed.
  - Tools with a plain JSON Schema, including MCP tools, work on runtimes that forbid code generation.
  - A bad schema fails at registration or, if first supplied during a turn, before the provider call that uses it.
  - A tool-admission failure reports its real cause and leaves the branch usable.
  - Validation performance on large schemas may be lower than Ajv's compiled code. Tool schemas are small, and the spike records a measurement.
  - The conformance verifier keeps precompiled Ajv (ADR-0082 decision 4), so the verifier and production do not share one validator's blind spots.
  - `@tuvren/core`, `@tuvren/runtime`, `@tuvren/runner-react`, `@tuvren/sdk`, `@tuvren/mcp-client`, and `@tuvren/provider-bridge-ai-sdk` change behavior and need changesets.
