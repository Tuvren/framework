### ADR-0052 Side-Effect-Once Under Preemption via an Idempotency Envelope

- **Status:** accepted; §1 amended by **ADR-0065**, and §2 clarified for cold recovery. The identity is derived from `(turnId, callId)`, not `(runId, callId, fencingToken)`. The original triple could not satisfy this ADR's own "same identity for the same logical call" promise. A Run is one execution *attempt*, and the fencing token rotates on every lease renewal. The no-retry rule applies to the live owner after authority loss. Framework specification §4.9 and owner ruling R1 govern cold missing-call recovery by a replacement owner.
- **Context:** PRD v0.10.0 CAP-P0-068 and Architecture v0.10.0 (Side-Effect-Once Under Preemption Model) require a recovery design that lets an external system deduplicate an uncertain side effect. ADR-0050 removes lease-expiry clock skew, but a residue remains in every multi-worker topology: an external call (a charge, a send, or a remote write) can be in flight when a worker loses execution authority. Fencing protects the runtime's own database, but it cannot determine whether the external system completed that call. The capability-orchestration work already added the needed metadata: `TuvrenToolDefinition` carries `idempotent?`, `nonRetryable?`, and `maxRetries?` (ADR-0046/ADR-0047, §3.13/§4.21), the kernel issues a monotonic `fencingToken` per lease, and recovery skips completed tool calls by `callId` (`docs/KrakenFrameworkSpecification.md` §4.9). The remaining requirement is to apply this metadata at the preemption window and propagate a stable idempotency identity to the system that executes the effect.
- **Decision:** Reuse the existing metadata rather than inventing new fields, and add a derived idempotency envelope:
  1. **Idempotency envelope.** As amended by ADR-0065, side-effecting invocations carry an idempotency identity derived from `(turnId, callId)`. The Tuvren-server tool path and the Client Endpoint Boundary dispatch envelope both carry the identity. A tool implementation or client environment must present it to the external system for deduplication. Every re-dispatch of the same logical call presents the same identity.
  2. **No retry by a live owner after authority loss.** This rule applies when a live owner loses its Run lease while a call is in flight. If renewal fails on a stale fencing token, the framework invalidates the handle. The dead or fenced owner must not retry that call after fencing, and it must not persist a late result. For an invocation marked `nonRetryable`, the `nonRetryable: true` setting also continues to override `idempotent: true` in the retry budget, per ADR-0047 and Epic BB.
     Cold recovery by a replacement owner follows a different rule. Under owner ruling R1 and framework specification §4.9, the replacement Run dispatches every original call that has no durable result, including a call marked `nonRetryable`. It uses the original `turnId`, `callId`, and derived idempotency key. The replacement Run does not dispatch calls with durable results. When the first attempt's external outcome is unknown, the external system must deduplicate the repeated key.
  3. **Client-result-as-proposal.** A client-reported result is a proposal; it becomes durable state only through a runtime commit performed under a valid run fencing token, so a stale or late client report (after lease loss or lease expiry) can never mutate committed history. This composes the run lease (write authority) with the client-endpoint lease (availability/staleness) without conflating them.
- **Consequences:** The framework guarantees stable key presentation, prevents a dead or fenced owner from retrying `nonRetryable` work, and accepts durable writes only under valid authority. These guarantees do not make an external effect occur once by themselves. Tool authors, client environments, and external systems must carry and deduplicate the supplied identity. The shared checks `runtime-lifecycle-ext.stale-recovery.interrupted-batch-dispatches-missing-set` and `runtime-lifecycle-ext.stale-recovery.interrupted-batch-preserves-idempotency-keys` prove that cold recovery dispatches the missing set and preserves the observed keys. They do not execute an external deduplication system or claim that the effect occurred once. No new tool-definition fields are introduced. `docs/KrakenFrameworkSpecification.md` records the live-owner rule, the cold-recovery rule, and the client-result-as-proposal invariant.
